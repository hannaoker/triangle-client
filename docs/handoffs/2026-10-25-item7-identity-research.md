## What exists today (verified in code and docs)

1. **Local profile instance ID**: lowercase SHA-256 of `triangle-client-instance-v1` + NUL + the profile name (`docs/triangle-client/threat-model.md`; `scripts/triangle-client-service.sh` `registry_state`). Device-local: the same profile name on two machines gives the same ID, so it is neither globally unique nor proof of anything. It is the 64-hex `senderId` of workers (for example `gravity2`), of the bound Codex conversation, and of the paired Claude identity; Grok contexts are hash-paired exact IDs.
2. **Local session address**: `session-` + SHA-256 of `installationId`, workspace and the harness session id (`codex:`-prefixed for Codex); raw ids never stored. Scoped to one discovery installation on one device (`local-messaging-interactive-session.mjs`, `sessionAddress`).
3. **Local credentials**: supervisor-held HMAC turn credentials with claims (`senderId`, `senderType`, `sessionId`, `generation`, `bindingId`, `allowedRecipients`, TTL). Valid only on the local socket; not exportable proofs (`local-agent-messaging.md`).
4. **MESH principal**: `agent_[a-f0-9]{32}`, immutable and never reused; handle is a human alias unique in one home-server namespace; federation prohibited until Phase 6 (ADR 0001, 0002 in the server repo `docs/adrs/`). Terms already separated there: principal, controller (human, WebAuthn), runtime, credential, endpoint, profile ("an endpoint or profile can change without changing the principal"; "no recovery attempt may infer authority from an endpoint, profile, display name, mailbox history, or a bearer alone").
5. **MESH credentials**: Ed25519 workload JWT, claims `iss, sub (agent id), aud, workload_id, scope, iat, exp, jti, rev (revocation epoch), cnf.jkt (DPoP)`, verified against the issuer key and the principal's current epoch (`mesh/app/lib/workload-token.ts`). Signing keys in managed KMS; recovery by overlapping keys, delayed WebAuthn dual-control (ADR 0001). Trust root is the home server (I6-A); mailbox event origin is server-recorded attribution, not a principal signature.
6. **MESH peer tickets** (`mesh/app/lib/peer-auth.ts`): `mesh_peer_` opaque bearer, at most 300 s, minted by a sender for one recipient agent; the insert snapshots the sender's `dm.send` epoch and the recipient's `dm.receive` epoch; lookup returns the sender's id, name and endpoint URL; at most 100 active per sender. Permissions (`dm.send`, `dm.receive`, `directory.listed`) carry epochs. This is already a server-attested "S may message R" statement, but verification needs a MESH lookup.
7. **Client binding of a profile to a MESH agent**: `triangle agent add` writes `<TRIANGLE_HOME>/agents/<agent_id>/workload-key.json` and `agent.json`; the helper `bind` writes a pointer `profiles-v1/profile-<hex>.json` after proving the identity live with a DPoP `GET /api/v1/agents/me` (`workload-credential.mjs`, `threat-model.md`). Same-user runtime can read the custody home (decision F1).
8. **Iroh** (`packages/peer-engine`): one persistent device `SecretKey` per state dir (`identity/device.key`, 0600); the endpoint id is the public key. Inbound is admitted only if the TLS-authenticated endpoint id is on a static roster (`--allow-peer`/`--roster`; empty admits nobody); `sender_endpoint_id` must equal the connection identity (`sender_mismatch`); message ids must be globally unique (7-day tombstone window). The README lists signed roster admission, **Triangle identity ↔ Iroh binding** and hybrid MESH/Iroh routing as out of scope. Supervisor `peerWakes` entries map a local profile and `profileInstanceId` to a peer-engine state root; nothing there names a principal.
9. Physical Iroh proof (2026-10-20): relay path works between the two Macs; direct path unresolved; separate-network NAT traversal unverified.

## Gaps against the six acceptance gates

- No object ties one logical agent to its local profile, its sessions, its Iroh endpoint and its MESH agent; today they are joined only by owner configuration and by equal names.
- A device key authenticates the device, not an agent on it; two agents on one device share one endpoint identity.
- No cross-transport sender proof: local credentials are local, Iroh proves only the device, MESH proves its own principal.
- No rotation, revocation, expiry, device-loss or multi-device story for Iroh endpoints; no offline-validity rule for any assertion.
- No inspectable identity view (`status`/`doctor` show instance ids and presence, not principals, bindings or authority).
- Migration risk: equal profile names across devices and name-based matching must never merge identities.

## Planned outline and recommended decisions (for the document)

1. Goals, non-goals, the vocabulary (reuse the MESH ADR terms; add session and conversation as local runtime references).
2. Model: a **principal** is the logical agent. Managed: the MESH agent ID is authoritative. Serverless: a self-certifying local principal ID derived from a per-agent identity public key. A **binding** is a signed or owner-approved statement joining a principal to one reference (local profile instance, session address, Iroh endpoint id, MESH enrollment). Sessions and device keys are never principals. Namespaces: `agent_…` (MESH), a distinct prefix for local principals, `session-…`, 64-hex instance ids; collisions are detected, never merged by name.
3. Trust modes and who signs: managed = MESH issuer signs an expiring **endpoint delegation** (extend the workload-JWT pattern: `sub` agent, `cnf` the Iroh endpoint key, `scope` dm.send/dm.receive, `jti`, `rev`), minted over an authenticated workload call; peer tickets stay the online alternative. Serverless = **pairing**: an invitation carrying endpoint keys and principal public keys, approved by the owner on both sides, recorded as a pairing with optional expiry. No automatic cross-mode merge, enrollment, content bridge or downgrade.
4. Sender provenance: a typed envelope field `{principal, via:{transport, authenticatedPeer}, assurance:{kind: local-attested | mesh-recorded | delegation-verified | owner-paired, verifiedAt, expiresAt}}` computed by the receiver, never copied from the payload; local HMAC credentials never leave the host; a device with several agents needs a per-agent proof, not just the endpoint key.
5. Reply routing: bind a reply to the authenticated original principal, conversation and binding generation; re-verify at reply time; never fall back to another active session or another endpoint.
6. Lifecycle: key and session rotation, revocation (MESH epoch, owner removing a pairing), expiry, device loss, re-enrollment and multi-device delegation; explicit offline-validity window and revocation-freshness rule per mode; rotation never creates a replacement principal silently.
7. Migration: read-only inventory first (derive today's bindings from config and `profiles-v1`), owner-confirmed mapping, no name-based merge, rollback by ignoring the registry.
8. Inspectable view in `status`/`doctor`: principal, kind, bindings with authority and expiry, freshness, conflicts; no secrets.
9. Verification plan mapped to the six gates (positive and negative tests per mode; installed-path evidence; two physical machines for the Iroh gates), implementation slices (read-only view and registry first; serverless pairing; managed delegation, which needs a server change in the `the-triangle` repo; then item 6 consumes it), rollout and rollback.
10. Open owner decisions: serverless principal ID format and prefix; assertion lifetime and offline grace; whether peer tickets or a signed delegation is the managed default; whether one device key may serve several principals or each principal gets its own endpoint key; who approves a pairing (owner only).
