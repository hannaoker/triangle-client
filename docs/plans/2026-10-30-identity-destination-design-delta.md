# Identity and destination design delta (U3)

Status: design delta, 2026-10-30, corrected the same day after an independent model review (not a human or Codex review). Design and review only: this document authorizes no code, runtime, binding, grant, enrolment, installation or network route, and it is not owner-approved. Baseline: U2 head `27d63d3` (draft PRs #148 and #149, not merged) on client main `741ff27`. It supplements `2026-10-25-identity-reconciliation-design.md` (the identity design) and `2026-10-25-unified-messaging-interface-design.md` (the interface design) and leaves their cryptographic, rotation and lifetime proposals alone. Every claim about shipped behavior cites source at this baseline; paths are under `packages/agent-worker/src/` unless they start with `docs/`, `test/` or `packages/`.

## Purpose

U3 of `2026-10-29-unified-messaging-next-slices.md` asks for the identity and destination design to be closed before any Iroh or MESH adapter is built. This delta says what exists today, where the October text no longer matches the code, which rules to adopt, and which owner decisions are still open. The owner decisions of 2026-10-25 (identity design decisions 1 to 7, interface design decisions 1 to 8) stay in force and are not reopened, except that interface decision 4 (one release train) was superseded by R1 plan decision 1. Nothing here maps a session to a principal, pairs a peer or activates R2.

## 3. Rules to adopt

### A. Session-to-principal authority

1. Until the owner decides otherwise (D4), no discovered session or attached chat has a principal, and a `session-` address is never a principal. Every observation for them keeps `principal`, `authorityOrigin` and `bindingGeneration` null. This is the shipped behavior and needs no change. It is separate from the paired Codex and Claude conversations: their 64-hex profile identities sit in the router directory (row 9) and can be registry-mapped and addressed by principal like any profile.
2. A principal's authority comes only from an owner-created registry record. It never comes from a label, a caller-supplied field, a harness type or a same-harness profile (the rule the code already states, `local-sender-authentication.mjs:6-9`).
3. If chats are ever mapped, the record names a selector, not a session id: harness plus workspace, the same shape as the recorded destination rule. Every new chat is a new address (`local-messaging-interactive-session.mjs:215-217`) and ended sessions leave after 8 days, so a pinned address goes stale. A selector alone would let any chat that becomes the only live attached session in the workspace inherit the authority, which is the newest-session substitution the plan rules out. So the owner also confirms each chat once, and a second matching chat drops both to unbound. This replaces the supervisor-issued per-session binding of identity design 4.2.
4. The supervisor derives a mapped observation from the live registry and the live attachment, never from message metadata (`local-reply-route-contract.mjs:9-11`). The contract already accepts a mapped principal (`:12-29`) but no shipped path supplies one, so pins exist today only between unbound chats (row 6). Once mapped pins exist they would record principal, authority origin and binding generation.
5. Today's gate for registry writes is a terminal plus a plan id (`packages/triangle-cli/src/cli.mjs:352-371`). It does not stop a same-user agent with a pseudo-terminal from confirming (identity design 8, "Implemented first cut"). Creating, moving or revoking a chat mapping, or moving a profile to another principal, therefore needs a stronger gate (D5).

### B. Revocation and generation

| Counter | Lives in | Advances | Fences |
| --- | --- | --- | --- |
| `binding_generation` | registry binding, profile to principal | +1 on a rebind (`identity-registry.mjs:1355`); `revoke` leaves it unchanged; no delete action | New principal resolutions: the snapshot provider re-reads when the registry file's stat key changes and at least every 2 s (`router-registry-snapshot.mjs:128`, `:149-160`); the resolver ignores revoked bindings (`recipient-resolver.mjs:121-130`) |
| lifecycle `generation` | discovered-session row | +1 on a start after an end (`local-messaging-journal.mjs:2149`); restarts at 1 once the row and tombstone are pruned after 8 days | Attach (`session_fenced`, `local-messaging-interactive-session.mjs:305`) and every later request (`:314-315`) |
| child id (`bindingId`) | attachment and credential | a new MCP child | The same `validateRequest` check |
| pin generations | reply pin | observed; may not regress | Replies (`local-reply-route-contract.mjs:49-58`) |

1. Revoking a profile binding removes the principal address form for that profile. It does not block delivery: exact-id sends keep routing, because the owner ACL, not the registry, authorizes ids (`unified-router.mjs:238-281`). Blocking delivery stays an owner policy change.
2. A rebind that changes `principal_id` should be its own owner-confirmed action naming the old and the new principal, and storage should refuse it as a plain `bind` (D2). That restores the October `ERR_BINDING_CONFLICT` intent.
3. Intended behavior once mapped pins exist: a pinned conversation whose party later moves to another principal fails closed (`reply_remote_mismatch`) instead of being rerouted (`local-reply-route-contract.mjs:49-72`). Today no pin involves a profile, so a profile move affects only new sends, and an unpinned worker conversation resolves afresh on its next send.
4. `binding_generation` never decreases in storage. The lifecycle generation is monotonic only while its row or tombstone is kept (8 days). After that it restarts at 1, and because pins are never deleted, a pending pinned reply can then fail with `reply_generation_regressed` (`local-messaging-journal.mjs:2132-2135`, `:2149`; `local-reply-route-contract.mjs:54-57`). Pruning or expiring pins, or a longer-lived tombstone, needs its own decision with the R2 follow-up. A restored older registry snapshot is not detected locally because the audit chain is unsigned (identity design 4.1 status note); R1 plan 3.7 records that risk as recorded, not mitigated.

### C. Principal-addressed inbound delivery

1. Today only local sends exist. A principal resolves to the one bound profile instance in the router's directory, or the send fails (`recipient-resolver.mjs:132-183`).
2. For remote inbound (not built), keep the recorded rule order (interface design 4.5; decisions 2 and 7): a headless runner profile uses the runner; a bound conversation uses that conversation; otherwise the principal's destination rule (harness and workspace) selects the one live attached session; with none the message holds as `no_destination`, with several as `destination_ambiguous`. The router never picks the most recently attached session and never a different profile. "Authorized" means the owner's receiver policy for that sender applies before matches are counted (the shipped analogue is `mayReceive`, `local-messaging-interactive-session.mjs:288`).
3. Two clarifications close gaps in the October text. First, a principal bound to several local profiles holds inbound as `destination_ambiguous`, and the owner resolves it by revoking a binding (or by D3-C's primary); a destination rule cannot choose between two runner profiles, because runner and bound-conversation profiles match first. Second, a held message and its candidate list are visible to the owner in `status`; the sender sees only a bounded reason code. This matches U2, where discovery never names candidates the caller cannot see.
4. New in this delta, not in the October text (which says only that `worker` and `mcp-interactive` profiles are left alone): one consumer per lane. A profile's inbound is owned by exactly one of the runner, a router-owned destination or the interactive adapter, and a configuration naming two is refused at load.
5. Pins for remote conversations key on the verified remote principal and request id (identity design 5), added beside the local key shape.

### D. Exact addresses and labels first; aliases later

1. The server and the agent-facing MCP surfaces accept exact ids only; labels in directories are display text. The owner CLI maps configured profile names (and `claude`) locally before sending, as interface design 4.2 form 2 keeps.
2. Aliases are a registry extension (an `aliases` map, set and clear commands, audit actions; R1 plan decision 3) that must exist before any remote adapter makes guessable names reachable. Contract: owner-set only; one alias names one principal in this registry; an alias that also matches a local id or label fails as `alias_unresolved` and never wins silently; the failure lists candidate ids only to a sender authorized for them; aliases never cross a transport (identity design 3, rule 5). Once aliases exist, telling an unknown alias from a not-allowed one becomes an oracle again (R1 plan 3.2) and is decided with the extension.
3. Until then principal sends work for `agent_` ids only, and `peer_` stays refused.

### E. What the review and reply authorization does not cover

The workspace `CLAUDE.md` and `_context.md` (owner decision, 2026-10-29) authorize reviewing Triangle Client source, plans and pull requests and sending a correlated reply to the bound Codex conversation when Triangle delivers the request from the verified sender. In addition to the exclusions `CLAUDE.md` already lists (code changes, merges, installs, delivery grants, credential access, changes to old queued or held work, harness tool permissions and Triangle delivery permissions), they do not cover: binding, rebinding or revoking a principal; peer pairing; enrolment into MESH; destination rules; aliases; session grants (`grant-session`); enabling reply pin admission (`reply-identity.json`) or the router (`router.json`); or copying local content to another transport.

### F. Prerequisites before an Iroh or MESH adapter (not designs)

1. A registry schema version that can hold `peer_` principals, `serverless-peer` bindings, aliases and destination rules (D1).
2. `admitInbound` with `origin_transport` and `remote_principal` columns, reply pins keyed by the remote principal, and a router-owned value added to the existing profile `deliveryMode`.
3. A command that sets and clears a destination rule, with audit.
4. Endpoint-to-principal binding, one principal per endpoint, with expiry, and the approval mechanism of identity design decision 4 (its feasibility check is still pending).
5. For MESH: the peer-endpoint registry and resolve API (identity design Slice 4, in the MESH server repository) and the 5 and 15 minute freshness rules.
6. Hold-after-receipt behavior, so a message acknowledged by the engine can still be held (identity design 4.3), and per-remote-principal inbound caps.
7. Fresh installed evidence for each step, then two-host and separate-network acceptance. Source tests establish none of it.

## 5. Evidence and limits

Read at the baseline: the source files cited above, the two October designs, the R1 plan and the R1 and R2 handoffs. The full `packages/agent-worker` suite passes on `27d63d3` (1291 tests, 3 skipped, 0 failures). Not read or verified: any installed or live state (including whether `reply-identity.json` or `router.json` is enabled now, and whether the paired conversations' profiles are mapped in the live registry), the MESH server, the Swift helper and the Rust peer engine, so the October claims about those stay as that design recorded them. A retry after a rebind was not traced end to end: besides the principal-intent check (`local-messaging-journal.mjs:320-340`) the journal also compares the stored envelope, and what that does when a rebind changes the resolved recipient was not traced. This delta describes no behavior it did not read in source.
